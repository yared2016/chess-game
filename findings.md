# Architecture & System Inspection Findings

**Project:** Castle 3D Multiplayer Chess Platform with Real-Time ETB Financial System  
**Date:** September 2026  
**Status:** Completed Phase 1 Inspection  

---

## 1. Current Architecture

The project is an online 3D chess platform structured as a full-stack Next.js application with a reactive Convex backend and Clerk authentication:

- **Frontend:**
  - Next.js 16 (App Router) with React 19.
  - Three.js, React Three Fiber (`@react-three/fiber`), `@react-three/drei`, and postprocessing for physically lit 3D chess environments.
  - 2D fallback board using SVG/canvas when WebGL2 is unsupported.
  - Tailwind CSS v4 with `@tailwindcss/postcss`, `lucide-react`, and standard shadcn/ui components (`card`, `button`, `badge`, `dialog`, `tabs`, `sonner`).
  - Stockfish chess engines (`stockfish 18` and `stockfish 11` fallback) running locally in Web Workers for evaluation and candidate generation.
  - Vercel Eve / AI SDK for persona-based opponent commentary.

- **Backend & Database:**
  - Convex 1.44 real-time serverless database.
  - Optimistic concurrency control (OCC) transactional mutations.
  - WebSocket subscription for live reactive state updates across matches, queues, and balances.
  - Clerk JWT authentication integration with Convex (`ConvexProviderWithClerk`).

- **Package Management:**
  - Node.js runtime, bundled with npm/pnpm.

## 2. Existing Convex Schema

The current `convex/schema.ts` defines the following tables:

1. **`players`**:
   - `clerkId`, `tokenIdentifier`, `username`, `usernameLower`, `avatarUrl`, `email`.
   - Ratings: `rating` (overall 1200), `ratingHuman`, `ratingAi`, `wins`, `losses`, `draws`.
   - Preferences: `roomPreset`, `boardView` (2d/3d), `qualityTier`, `postFxEnabled`, `proUntil`.
   - Indexes: `by_clerkId`, `by_tokenIdentifier`, `by_usernameLower`, `by_email`, `by_rating`, `by_ratingHuman`, `by_ratingAi`.

2. **`wallets`**:
   - `userId` (id to `players`).
   - `availableBalance` (number, currently stored as major units e.g. 100 ETB).
   - `lockedBalance` (number, stake locked in queue/game).
   - `totalDeposited`, `totalWithdrawn`, `totalWon`, `totalLost`.
   - `createdAt`, `updatedAt`.
   - Index: `by_userId`.

3. **`deposits`** (Legacy Manual Flow):
   - `userId`, `walletId`, `amount`, `code`, `screenshotId`, `senderInfo`, `status` (`pending`, `approved`, `rejected`), `rejectionReason`.
   - Indexes: `by_userId`, `by_status`, `by_code`.

4. **`withdrawals`** (Legacy Manual Flow):
   - `userId`, `walletId`, `amount`, `payoutMethod` (`telebirr`, `cbe`), `payoutAccount`, `status` (`pending`, `completed`, `rejected`), `rejectionReason`.
   - Indexes: `by_userId`, `by_status`.

5. **`commissions`**:
   - `gameId`, `amount`, `transferred`, `createdAt`.
   - Index: `by_transferred`.

6. **`games`**:
   - `whiteId`, `blackId`, `mode` (`online`, `ai`, `local`), `status`, `winner`, `endReason`.
   - `stake` (ETB per player), `escrowTotal`, `commission`, `payout`, `escrowSettled`.
   - Moves, FEN, PGN, turn, time clocks.

7. **`queue`**:
   - `playerId`, `rating`, `joinedAt`, `stake`.
   - Indexes: `by_joinedAt`, `by_playerId`.

8. **`challenges`**:
   - `fromId`, `toId`, `stake`, `status`, `gameId`.

9. **`presence`**: Real-time heartbeats and spectator tracking.
10. **`commentary`**: Move commentary generated by Eve.
11. **`ratingHistory`**: Historic Elo tracking.
12. **`notifications`**: Player notification records.
13. **`chapaPayments`** (Preliminary Test Payment table):
   - `userId`, `txRef`, `amount`, `currency`, `provider`, `status`, `chapaRef`, `checkoutUrl`.

## 3. Existing Clerk Authentication

- **Client:**
  - `<ClerkProvider>` wraps `<ConvexClientProvider>` in `src/app/layout.tsx`.
  - `<ConvexProviderWithClerk>` in `src/components/providers/convex-client-provider.tsx` automatically attaches Clerk JWTs to all Convex client queries and mutations.
- **Server:**
  - Next.js server components and API routes import `auth()` and `currentUser()` from `@clerk/nextjs/server`.
  - Protected pages under `src/app/(protected)/layout.tsx` invoke `await auth.protect()` which redirects unauthenticated requests to `/sign-in`.
- **Convex Backend:**
  - `convex/auth.config.ts` defines Clerk as the OpenID Connect JWT issuer.
  - `convex/lib/auth.ts`:
    - `requireIdentity(ctx)`: Extracts and asserts `ctx.auth.getUserIdentity()`.
    - `playerForIdentity(ctx, identity)`: Queries `players` table using `tokenIdentifier` (`<issuer>|<subject>`).
    - `requirePlayer(ctx)`: Guarantees authenticated and provisioned player row.
    - `requireAdmin(ctx)`: Checks `player.clerkId === process.env.ADMIN_CLERK_ID` (or falls back to the first created player).

## 4. Existing User Model

- Each user has a primary identity in Clerk (`user_...`).
- Synchronized to Convex via `ensurePlayer` mutation in `convex/players.ts`.
- Has an associated wallet in the `wallets` table created by `ensureWallet` in `convex/wallets.ts`.
- Profile fields include username, lowercased username for search, avatar URL, optional email, and Elo ratings for online and AI modes.

## 5. Existing Chess Match Model & Escrow Flow

- **Match Creation:**
  - Matchmaking via `convex/queue.ts`:
    - Player enters queue with a chosen `stake` (0, 10, 25, 50, 100 ETB).
    - Queue entry immediately moves `stake` from `wallet.availableBalance` to `wallet.lockedBalance`.
    - Pairing algorithm (`queue.pair`) creates a `games` row with `whiteId`, `blackId`, `stake`, `escrowTotal = stake * 2`, `commission = escrowTotal * COMMISSION_RATE (10%)`, `payout = escrowTotal - commission`.
  - Direct Challenge via `convex/challenges.ts`:
    - Challenger locks stake on creation; challenged player locks stake upon acceptance.
- **Match Finalization:**
  - Terminal conditions in `convex/lib/games.ts` (`finalizeGame`):
    - On checkmate, resignation, or abandonment timeout: winner's wallet gets payout credited, loser's locked balance is cleared, platform commission is recorded in `commissions` and credited to Admin's wallet balance.
    - On draw/agreement: both players refunded their locked stake.
- **Gaps Identified:**
  - Balance mutations currently happen via direct `ctx.db.patch(wallet._id, ...)` calls without an immutable ledger entry.
  - Floating point calculations (`totalPool * COMMISSION_RATE`) rather than integer minor units.
  - No explicit ledger transaction trail for auditability.

## 6. Existing Admin Model

- Admin is determined by matching Clerk ID against `ADMIN_CLERK_ID` environment variable.
- Secret admin interface is located at `src/app/(protected)/yyhnan/page.tsx` rendering `<AdminView />`.
- Public route `/admin` is deliberately configured to return `notFound()` as a security measure.
- Existing Admin capabilities in `convex/admin.ts`:
  - `platformStats`: Aggregates total commissions, total deposits, total withdrawals, active players, and admin wallet balance.
  - `markCommissionTransferred`: Marks commission records as transferred.
  - `syncCommissionsToWallet`: Backfills accumulated commissions to admin wallet.
  - Manual deposit approval/rejection and withdrawal payout processing.
- **Gaps Identified:**
  - No capability to freeze/unfreeze wallets.
  - No financial reconciliation dashboard (Chapa transactions vs internal records).
  - No audit log for administrative financial interventions.
  - No inspection for provider transaction fees vs platform revenue.

## 10. Best Location & Boundary for the Financial Domain

To ensure that the financial core remains independent of Chapa and any future provider:

1. **Convex Financial Core (`convex/financial/` or `convex/` modules):**
   - `convex/schema.ts`:
     - Add `wallets` state flags (`status: "active" | "frozen" | "restricted"`).
     - Add `financialLedger` table: immutable double-entry/single-sided audit trail with integer minor units.
     - Add `financialDeposits` table: provider-agnostic internal deposit records.
     - Add `financialWithdrawals` table: provider-agnostic internal withdrawal records with reservation states.
     - Add `financialAuditLogs` table: administrator and system audit records.
     - Add `financialConfig` table (or system config module): provider fee rates, platform commission rates, limits.
   - `convex/ledger.ts`:
     - Low-level immutable posting functions (`postLedgerEntry`).
     - Invariant enforcement (`availableBalance >= 0`, `lockedBalance >= 0`).
   - `convex/wallets.ts`:
     - Domain operations: `creditDeposit`, `reserveMatchEntry`, `releaseMatchEntry`, `settleMatch`, `reserveWithdrawal`, `completeWithdrawal`, `reverseWithdrawal`, `freezeWallet`, `unfreezeWallet`.
   - `convex/money.ts`:
     - Centralized minor unit (santims) conversion, rounding, and fee calculations.

2. **Payment Provider Abstraction (`src/lib/payments/`):**
   - `src/lib/payments/types.ts`: Interface definitions for `PaymentProvider`, `PaymentInitRequest`, `PaymentVerifyResult`, `TransferInitRequest`, `TransferVerifyResult`.
   - `src/lib/payments/fee.ts`: Centralized fee calculation logic supporting `ADDITIVE` and `DEDUCT_FROM_GROSS` fee modes.
   - `src/lib/payments/chapa/client.ts`: Dedicated Chapa API client encapsulating HTTP headers, URLs, and error decoding.
   - `src/lib/payments/chapa/adapter.ts`: Concrete implementation of `PaymentProvider` targeting Chapa API.
   - `src/lib/payments/provider.ts`: Provider resolver/factory allowing pluggable providers (e.g. Chapa, ArifPay, SantimPay).
